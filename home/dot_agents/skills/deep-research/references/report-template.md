**Load this reference when:** writing the report, choosing the deliverable shape, or deciding
where the file goes. It holds the nine-section contract, the claim language, and the gotchas.

# Report template

The default shape of the deliverable. Adapt the section names to what the user asked for; keep the
evidence discipline.

## The nine sections

```markdown
# [Research title]

## Executive summary
[Three to seven bullets, or one short paragraph. The answer first. The confidence, and the single
most important uncertainty, stated. Evidence ids on the high-impact claims.]

## Direct answer
[The user's core question, answered. Evidence ids inline: [E0001].]

## Key findings

### 1. [Finding]
- Claim: [the specific claim] [E0001]
- Why it matters: [the decision this bears on]
- Confidence: high / medium / low / unknown
- Uncertainty: none / single-source / weak / stale / contested / unknown

## Claim verification matrix
[Generated by `render` from the ledger. Do not hand-edit it.]

## Evidence table
[Generated by `render` from the ledger. Do not hand-edit it.]

## Contradictions and uncertainty
[The contradictions, the gaps, and the assumptions, each with its evidence ids.]

## Source-quality notes
[Primary against secondary, the independence of the sources, the freshness, and the bias that
mattered.]

## Method appendix
[Generated by `render` from the ledger: effort, hop count, source classes, counterevidence,
the run directory.]
```

Five sections are yours to write: **Executive summary**, **Direct answer**, **Key findings**,
**Contradictions and uncertainty**, **Source-quality notes**. Three are generated from the ledger:
**Claim verification matrix**, **Evidence table**, **Method appendix**.

Run `render` after the ledger is complete, then write the five sections over the placeholders.
Re-running `render` regenerates the three generated sections and **keeps** what you have written in
the other five — but if you add evidence after writing, regenerate and re-check the contradictions
section against the new rows.

## Calibrated claim language

| Verb | Use it when |
|---|---|
| `shows` | the source demonstrates the claim directly |
| `suggests` | the evidence is partial or context-dependent |
| `claims` | you are reporting what a source says, without endorsing it |
| `likely` | several signals align, but the direct proof is incomplete |
| `unknown` | the searched evidence does not settle the point |

Never upgrade a source's own claim into your finding. A README says the feature is production
ready; the report says the README claims it, and cites the code, the tests, and the issues that
bear on it.

## Evidence table rules

Every row must be specific enough for someone else to re-check it. A row reading "web search
results show…" is not evidence; record the source you opened, not the query that found it.

The generated table has one row per evidence id, with the source, the URL, the type, the quality
score, the stance, the date or version, the locator, and the claim. The generated tables carry
**bare** ids (`E0001`), not citations (`[E0001]`), so that a report which only fills the tables
still fails the lint check that asks for inline citations. Cite the high-impact claims inline, in
the prose, where a reader sees the claim and its source together.

## Where the report goes

Write the file where the repository already keeps such notes, or where the user says. If the
repository has no such place, put it somewhere sensible and say where in the reply. Then report
the path. A report that exists only in the conversation is a report nobody can re-check.

## Deliverable variants

### Memo

The nine sections, compressed. The executive summary carries the answer, the direct answer restates
it in two or three sentences, and the findings are three to five numbered items. The claim
verification matrix and the evidence table stay in full; they are the audit trail.

### Literature review

Add a literature map and an open-questions section:

```markdown
## Literature map
| cluster | representative papers | core idea | evidence | limitations |
|---|---|---|---|---|

## Open research questions
[What stays unresolved across the literature.]
```

Group the papers by idea, not by year, when the ideas differ: retrieval plus generation,
interleaved retrieve-and-reason loops, self-critique, multi-agent planners and executors, graph
or citation-network retrieval, factuality and citation-accuracy benchmarks, and the failure-mode
and contamination literature.

### Decision matrix

Add a comparison and a validation plan:

```markdown
## Comparison matrix
| option | strengths | weaknesses | evidence | fit |
|---|---|---|---|---|

## Minimum validation plan
[The smallest experiment that would remove the biggest uncertainty.]
```

A decision matrix without a validation plan is a preference with citations.

## When the user wants a short answer

Use the ledger anyway; compress the deliverable. Answer first, then three to five supported
findings, then one caveat paragraph, then a compact source list. Say that the full ledger exists
and where it is.

## Gotchas

The facts that defy a reasonable assumption. Each one has cost a run.

- **The arXiv API returns Atom XML, not JSON.** Read the feed with the `:raw` suffix or the XML is
  mangled. `read` on `arxiv.org/abs/<id>` and on `arxiv.org/pdf/<id>` returns markdown, so the
  abstract page and the paper itself need no special handling.
- **Semantic Scholar returns HTTP 429 without an API key.** The request is refused, not answered.
  Treat the service as optional, and never record "no citing papers" from a refused request.
- **The GitHub REST API allows 60 requests per hour without a token.** That is the whole budget
  for a run. `raw.githubusercontent.com` and `git clone` are not on that meter.
- **A project's README, its documentation site, its release notes, and its maintainer blog are
  one source family.** Four URLs, one organisation. Counting them as four independent sources is
  the most common way a due-diligence report reaches the wrong conclusion.
- **An arXiv identifier without its version suffix drifts.** Cite the version you read
  (`1706.03762v1`); a later revision can change the abstract and the numbers.
- **Stars measure attention.** They are not evidence of correctness, of maintenance, or of
  production readiness.
- **A search-result snippet is a lead.** Logging evidence from a snippet is how a fabricated
  finding enters a report.
- **`render` writes the report from the ledger.** A hand-transcribed evidence table is the step
  where a number changes; let the script write it.
- **The ledger records what was checked.** It cannot prove a source was read. Say so in the method
  appendix, which the generated appendix already does.
- **A stale source is not a wrong source.** It is a source with a date, and the date belongs in
  `date_or_version` and `freshness_status`.
