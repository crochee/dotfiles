**Load this reference when:** choosing a diagram level, or checking that a diagram is honest about ownership and direction.

# C4 Views

C4 is four zoom levels over one system, each answering one kind of question. The levels exist to stop diagrams from mixing audiences: a context diagram that shows a connection pool is no longer a context diagram, and a container diagram that shows classes is a class diagram with extra steps.

## The four levels

| Level | Question it answers | Shows | Audience | Deliberately omits |
|---|---|---|---|---|
| 1 — Context | Who uses the system, and what does it depend on that we do not own? | People, the system as one box, external systems | Anyone, including non-engineers | Internal services, stores, protocols, technology choices |
| 2 — Container | What runs, what stores data, and who talks to whom? | Deployable units, data stores, message channels, protocols between them | Engineers, operators, security review | Classes, modules, schemas, framework internals |
| 3 — Component | What is inside one container, and where are its boundaries? | Components and their responsibilities inside one deployable unit | The team that owns that container | Hosts, other containers, database schemas |
| 4 — Code | What does this class or function do? | Classes, interfaces, call chains | The author, at the moment of writing | Everything above |

Level 4 is usually generated from code and rarely worth maintaining by hand; if it is stale it is worse than absent. The working set for architecture decisions is levels 1 and 2, with level 3 used sparingly.

## What belongs on each level

**Context.** People as named roles (not "user"), the system as a single box, external systems it calls or is called by, and the reason each relationship exists. A data store is not a context-level element: it is part of the system unless a separate team owns it, in which case it is an external system and must be drawn as such.

**Container.** One box per deployable unit: a service, a front-end app, a scheduled job, a worker, a database, a queue. Each box names its technology because the technology is part of the decision at this level ("PostgreSQL", "Node.js"). Each arrow names the protocol and the direction of the call. A container is something that can be deployed or restored independently; if two boxes always deploy together, they are one container.

**Component.** Only when a boundary inside one container is contested — a module split, an event-publishing path, a plugin interface. Group components by responsibility, not by file layout, and show only the dependencies that cross a responsibility boundary.

## What must not appear

- **Technology on a context diagram.** Level 1 shows what the system is for and what it depends on, not how it is built; a framework name there redirects the conversation to the stack.
- **Libraries, ORMs and internal modules on a container diagram.** Level 2 names the container's runtime or framework because that is what the container is ("React app", "Go service"), and names its store engine. It does not descend into libraries, connection pools, migrations or module layout — that is level 3 or code review.
- **An arrow without a protocol at level 2.** The protocol is the part a reviewer can check; without it the arrow asserts only that two boxes are somehow related.
- **Bidirectional arrows without a stated direction.** `A <--> B` hides which side initiates, and the initiator is the side that needs timeouts, retries and an owner for the failure. Draw two arrows or one arrow labelled with the call direction and the reply.
- **Boxes that no one deploys.** Every container maps to an artefact — an image, a binary, a job, a managed store, a channel. A box with no artefact is a wish, and it will outlive the project that wanted it.
- **Colour used decoratively.** One fill for external elements, one for internal, one for stores. If colour needs a legend longer than three entries, it is carrying meaning that belongs in labels.

## When to stop at level 2

Stop when the reader can answer the question that prompted the diagram: who calls whom, what runs where, what breaks when a box fails, and which boundary a change crosses. That is almost always level 2 for a service topology and level 1 for a system in its environment.

Go to level 3 only when one of these is true:

- A module boundary is being argued about and the argument is about what sits inside the container.
- A cross-cutting concern (authentication, event publication, caching) runs through several components and its path is not obvious.
- A new team is taking ownership of one container and needs the internal map.

Going deeper without one of these produces a diagram that repeats the code and is stale within a sprint.

## Notation discipline

| Rule | Why |
|---|---|
| One owner per arrow | The initiator owns timeout, retry and fallback. Two owners means neither implements any of them |
| Numbered interactions, with a table beside the diagram | Numbers survive layout changes; a long arrow label does not, and the table can carry the protocol, payload and failure behaviour |
| Direction of dependency drawn, not implied | The arrow shows who must be available for the caller to work; reversing it changes the failure domain |
| External systems visually distinct | Reviewers need to know instantly which failures are not fixable by the team |
| One diagram per question, one scope label | "Container view: orders, scope: checkout path" prevents a diagram serving two audiences |
| Shapes carry one meaning each | Person, system, container, store — four shapes, no more. A shape reused for two meanings is decoration |
| Legend on the diagram or in the caption | A diagram that needs a legend nobody wrote is a puzzle |

## Keeping a diagram honest

A diagram is a falsifiable claim. Check it against the repository:

1. Every container has a matching deployable artefact in the build or deployment configuration. List the path; if you cannot, delete the box or mark it `planned`.
2. Every arrow has a caller in the code — a client, an SDK, a connection string. An arrow that only exists in the diagram is a claim about intent, not about the system.
3. Every external system has an owner outside the boundary and a contract you can name.
4. Every store has a writing service named. A store written by two services is a shared-database boundary violation, and the diagram is where it becomes visible.
5. Every `planned` element is visually distinguishable from a delivered one, and the caption says when it lands.

Run this check whenever a diagram is updated, not once at design time. The diagram drifts first; the code follows.

## Diagram hygiene

- Keep the diagram source in the repository next to the document that embeds it, in a `docs/diagrams/` directory, and commit the rendered output only if the reader cannot render.
- One file per view, named by level and scope: `context-orders.mmd`, `container-checkout.mmd`.
- Do not exceed roughly twenty elements on a level-2 diagram. Beyond that, split by scope rather than shrink the text; a diagram nobody can read at 100% zoom is a table pretending to be a picture.
- Number the interactions and keep the table in the same file or the paragraph below it. When the diagram is re-laid out, the numbers still mean something.
- State the render command in the document. A diagram that cannot be rebuilt is a screenshot.

## A useful sequence for drawing

1. Write the question the diagram must answer, in one sentence, at the top of the file.
2. Choose the level from that question — not from what is easy to draw.
3. Place people and external systems first; they constrain the boundary.
4. Place containers inside the boundary until the question is answerable; stop.
5. Add arrows only for interactions the question needs, each with initiator, protocol and number.
6. Run the honesty check above, then delete every element that survived only because it was already on an older diagram.
