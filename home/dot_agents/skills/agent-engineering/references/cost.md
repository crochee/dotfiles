**Load this reference when:** accounting tokens per phase, designing a cacheable prefix, choosing a model per step, or attributing a cost spike to its cause.

# Cost

Cost is a property of the loop and the tool surface, not of the user's request. Two runs of the same task can differ tenfold because one re-sent a large tool schema on every step and the other did not.

## Accounting per phase

Measure where the tokens go before optimising anything. Four phases, recorded separately:

| Phase | What it includes | Typical share | Lever |
|---|---|---|---|
| Planning | System prompt, task, registry, plan drafting | 5–15% | Smaller model, shorter system prompt |
| Iterations | Re-sent prefix × step count, model output, reasoning | 50–70% | Fewer steps, cached prefix, smaller tool set |
| Tool results | The data the tools return | 15–35% | Page size, item caps, structured fields |
| Verification | Acceptance checks, grader calls, final review | 5–15% | Deterministic checks over model grading |

Two numbers per run are worth keeping permanently: **tokens per successful task** and **steps per successful task**. Both are scale-free and both regress visibly when something breaks.

## Cacheable prefixes

Most providers bill a repeated prefix at a discount if it is byte-identical and marked cacheable. The prefix is everything before the variable part, in this order:

```text
[ system prompt ] → [ tool schemas ] → [ stable context / registry ] → [ task and history ]
```

Order matters: the cache boundary is a prefix, so anything variable placed early invalidates everything after it. Practical rules:

- Put the system prompt and tool schemas first and keep them frozen for the life of a run. A tool description that embeds the current date, a request id or an incrementing counter invalidates the prefix on every call and is the most common self-inflicted cost.
- Serialise tool schemas deterministically. A map iterated in nondeterministic order produces byte-different schemas and a cold cache, with no visible code change.
- Treat the tool set as a release artefact: adding or removing a tool rewrites the prefix, so batch tool changes rather than shipping one per commit.
- Caches expire. A long run should assume two or three refreshes; a plan that assumes a warm cache for an hour is a plan that works in testing and not in production.

A cache invalidation is invisible in the output and visible only in the cost. That is the argument for logging the prefix hash per run.

## Tool results versus prompts

Prompts are written once and read by a person; tool results are generated by a machine and paid for repeatedly.

- A 30k-token tool result sits in the history for every subsequent step. At ten remaining steps it costs 300k tokens of input, most of it irrelevant.
- Cap by items, not characters: return 20 rows and a cursor rather than a truncated text blob. The next step re-fetches what it needs for 2k tokens instead of carrying 30k forever.
- Summarise a large result at the boundary: counts, ids, the first page, the cursor. Keep the raw payload on disk and reference it by path.
- Prefer fields the model will use. A record with 40 upstream fields and 6 useful ones costs 34 irrelevant fields per row per step.

## Model tiering

Match the model to the step, not to the product. Tiering is the largest single lever after prompt discipline.

| Step | Tier | Why |
|---|---|---|
| Multi-step planning, diagnosis of a failure | Strongest available | Errors here are multiplied by every later step |
| Routine tool selection with a clear schema | Mid | The schema carries the decision |
| Extraction, classification, formatting | Small | Bounded input, bounded output, checkable result |
| Bulk summarisation of tool results | Small | The output is compressed text, not judgement |
| Grading an eval assertion | Mid, with the rubric in the prompt | A cheaper grader with a rubric beats an expensive one improvising |
| Final review of a high-stakes artefact | Strongest | The last chance to catch a systematic error |

Do not tier the step that decides whether the run succeeded. A cheap acceptance check that passes bad work costs more than the tokens it saved. Re-measure the pass rate after any tier change — a smaller model that "obviously can do this step" often cannot, and the eval says so.

## Batching

- One call with ten items beats ten calls with one item, provided the output stays parseable. The saving is the re-sent prefix, which dominates small calls.
- Batch reads of independent records; do not batch writes whose order matters.
- Do not batch across steps that depend on each other: a batch hides the intermediate state the next decision needs.
- Batch size is bounded by output quality and by the response limit; a batch whose answer is truncated is more expensive than two smaller ones.

## Regression thresholds

Compare **cost per successful task**, not cost per run. A run that costs half as much and fails twice as often is four times as expensive per success.

| Metric | Warn | Block |
|---|---|---|
| Cost per successful task | +10% | +20% |
| Tokens per successful task | +15% | +25% |
| Steps per successful task | +10% | +20% |
| Cache hit ratio (where measurable) | −10 points | −25 points |

Measure the baseline over at least three runs and use the mean; single-run cost varies enough to produce false alarms. A regression that buys a documented pass-rate gain is a decision, not a violation — record both numbers next to the choice.

## Attributing a spike

Same task, same model, higher bill. The cause is almost always structural.

| Observation | Likely cause | Check |
|---|---|---|
| Input tokens up, steps flat | Prefix grew | Tool schema diff, system prompt diff, registry growth |
| Steps up, tokens per step flat | The loop is retrying | Stall signatures, tool error rate |
| Tool-result tokens up | Larger pages or a chattier upstream | Page size, item caps, upstream response size |
| Cache hit ratio dropped | Prefix changed or reordered | Prefix hash per run, schema serialisation order |
| Cost up on the same tokens | Model tier or price table changed | The model id recorded in the run log |
| Cost up only under concurrency | Rate-limit retries | 429 counts, backoff behaviour |
| Cost up after a prompt tweak | A longer system prompt invalidated every cached prefix | Compare system prompt length and tokens before and after |

The run log must contain, per step: model id, input tokens, cached tokens if reported, output tokens, tool names called, cumulative cost. Without the per-step split, a spike can be located only by bisecting commits — which works, but costs a day.

## A worked comparison

Two implementations of the same agent, same task set.

| | A | B |
|---|---|---|
| Steps per task | 14 | 9 |
| Tool schemas | 42 tools, 18k tokens | 11 tools, 4k tokens |
| Tool result size | full payloads, 22k mean | paginated, 3k mean |
| Prefix cacheable | no (schema included a timestamp) | yes |
| Tokens per task | 310k | 61k |
| Pass rate | 17/20 | 18/20 |

B is five times cheaper and slightly better. The difference is not a clever prompt: fewer tools, smaller results, and a prefix that stops changing. Cost work is mostly subtraction.
